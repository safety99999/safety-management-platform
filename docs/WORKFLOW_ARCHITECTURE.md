## 1. 문서 목적 및 위치

### 1.1 문서 목적

이 문서는 안전관리 플랫폼의 **전체 시스템 아키텍처와 업무 흐름**을 정의한다.

기존 개별 앱(안전정보 제공서, 안전퀴즈, 작업허가서, TBM, 위험성평가, 작업중지권)은 각각 독립된 기능이 아니라 **하나의 연결된 안전관리 프로세스**로 통합되어야 한다.

이 문서는 다음 목적을 갖는다.

- 프로젝트 최상위 워크플로우 확정
- 작업관리대장 서버와 안전관리 앱의 연동 구조 정의
- 도급인 / 수급인 역할 분리 명확화
- 30단계 업무 흐름 표준화
- 5단계 사용자 권한 체계 확정
- Phase A (수동) → Phase B (자동) 전환 로드맵 수립
- AI 위험성평가의 정확한 위치 정의
- 각 앱의 역할과 연결 관계 명확화
- 상태 관리 및 필수 게이트 정의
- 관리자 권한 및 데이터 무결성 정책

### 1.2 문서 위치

이 문서는 **프로젝트 최상위 아키텍처 문서**로서, 기존 세부 문서들의 상위 개념을 정의한다.

문서 참조 관계:

WORKFLOW_ARCHITECTURE.md (최상위, 이 문서) ├─ PROJECT_CONVENTIONS.md (기술 규약) ├─ HIGH_RISK_WORK_POLICY.md (고위험 정책) ├─ PAPER_FORM_DIGITAL_MAPPING.md (전자화 매핑) ├─ DB_SCHEMA.md (데이터 스키마) ├─ PERMIT_DB_SCHEMA.md (허가서 스키마) ├─ JSA_DB_STRUCTURE.md (JSA 구조) ├─ FIRESTORE_SECURITY_RULES.md (보안 규칙) └─ PROJECT_HANDOVER.md (인수인계)

단, 최신 법령 및 사내기준은 모든 문서보다 우선한다.

## 2. 시스템 전체 개요

### 2.1 시스템 구성

본 시스템은 **두 개의 축**으로 구성된다.

┌─────────────────────────────────────────────┐ │ [작업관리대장 서버] │ │ D-1 이전: 계획 수립 및 확정 │ │ ───────────────────────────── │ │ - 작업 등록 │ │ - 작업표준 / 위험성평가 / 작업계획서 │ │ - 안전정보 사전 준비 │ │ - D-1 사전회의 및 확정 │ └────────────────┬────────────────────────────┘ │ 확정된 계획 데이터 전달 ↓ ┌─────────────────────────────────────────────┐ │ [안전관리 앱] │ │ D-Day: 현장 실행 및 관리 │ │ ───────────────────────────── │ │ - 안전정보 제공서 (도급인 → 수급인) │ │ - 출입자 안전퀴즈 │ │ - AI 위험성평가 │ │ - 안전작업허가서 │ │ - TBM │ │ - 현장 안전점검 │ │ - 작업중지권 │ │ - 전자종결 │ └─────────────────────────────────────────────┘


### 2.2 계획 vs 실행 분리 원칙

**계획 (PLAN)**과 **실행 (EXECUTE)**을 명확히 분리한다.

| 구분 | 시점 | 시스템 | 담당 |
|---|---|---|---|
| **계획** | D-1 이전 | 작업관리대장 서버 | 도급인 + 수급인 (사전 회의) |
| **실행** | D-Day | 안전관리 앱 | 수급인 + 작업자 |
| **감독** | D-Day | 안전관리 앱 | 도급인 관리자 + 안전관리자 |

**원칙**:
- D-1에 확정된 계획은 D-Day에 임의 변경 불가
- 변경 필요 시 **재검토 프로세스** 발동
- 계획 데이터는 실행 데이터와 별도 저장 (감사 대응)

### 2.3 핵심 결과물

이 시스템의 최종 결과물은 다음과 같다.

- **작업별 통합 리포트** (permitNo 기준)
- **일일 안전관리 리포트** (관리자용)
- **작업관리대장 반영 결과** (Phase B에서 자동 반영)
- **감사 대응 이력** (모든 단계의 전자 서명 및 로그)

## 3. Phase A / Phase B 이중 아키텍처

이 프로젝트는 **두 단계**로 진행된다.

### 3.1 Phase A: 수동 업로드 (현재 ~ 서버 완성 전)

**상황**:
- 작업관리대장 서버 개발 진행 중 (최종 단계)
- 서버 완성 전까지 관리자가 엑셀로 수동 관리
- 안전관리 앱은 이미 운영 가능

**데이터 흐름**:

[관리자 엑셀 파일] ↓ 수동 복사 [대시보드 붙여넣기 창] ↓ parseAndSave() [localStorage: safetyDatabase] ↓ Firestore 동기화 버튼 [Firestore: 작업DB 컬렉션] (현재 703건) ↓ 자동 조회 [안전관리 앱 사용자 화면]


**특징**:
- 관리자 개입 필수 (엑셀 업로드)
- 안전관리 앱 사용자는 Firestore에서 자동 조회
- 703건 데이터는 이미 정상 이관됨

### 3.2 Phase B: 자동 연동 (서버 완성 후)

**상황**:
- 작업관리대장 서버 완성
- 서버 ↔ Firestore 자동 API 연동
- 관리자의 수동 업로드 부담 해소

**데이터 흐름**:

[사내 작업관리대장 서버] ↓ 자동 API 연동 [Firestore: 작업DB 컬렉션] ↓ 자동 조회 [안전관리 앱 사용자 화면]


**특징**:
- 관리자의 엑셀 업로드 불필요
- 실시간 또는 주기적 자동 동기화
- 엑셀 업로드 기능은 **비상용으로 유지** (서버 장애 대비)

### 3.3 Phase A → Phase B 전환 시 고려사항

**전환 원칙**:

1. **Firestore 스키마 유지**: 두 Phase에서 동일 스키마 사용
2. **점진적 전환**: 병행 운영 기간 1~2주 권장
3. **데이터 검증**: 서버 데이터와 Firestore 데이터 정합성 확인
4. **롤백 준비**: 문제 발생 시 Phase A로 복귀 가능

**전환 체크리스트**:

- [ ] 서버 API 인증 방식 확정 (API Key / OAuth)
- [ ] Firestore 쓰기 권한을 서버에 부여
- [ ] 데이터 매핑 검증 (서버 필드 ↔ Firestore 필드)
- [ ] 중복 처리 정책 (workId 기준)
- [ ] 오류 처리 및 알림
- [ ] 관리자용 수동 업로드는 유지 (fallback)

### 3.4 Phase A 유지 시 주의사항

Phase A 기간 동안:

**해야 할 것**:
- Firestore를 정식 저장소로 사용
- 703건 데이터 무결성 유지
- 관리자 계정 보안 강화 (엑셀 업로드 권한)
- 정기 백업 (Firestore 자체 백업 + 수동 백업)

**하지 말아야 할 것**:
- localStorage를 정식 저장소로 사용
- 관리자 없이 사용자가 직접 데이터 수정
- Firestore Rules를 완전 개방 상태 유지

## 4. 6대 원칙 (PLAN → CLOSE)

이 시스템은 다음 **6단계 원칙**을 따른다.

### 4.1 원칙 1: PLAN (계획)

**질문**: 무슨 작업을 어떻게 할 것인가?

**시점**: D-1 이전

**시스템**: 작업관리대장 서버 (Phase A: 관리자 엑셀)

**활동**:
- 작업 등록
- 작업표준 확인
- 위험성평가 초안
- 작업계획서 작성
- 안전정보 준비

**책임자**: 도급인 작업담당자, 수급인 작업책임자

### 4.2 원칙 2: REVIEW (검토)

**질문**: 이 계획대로 작업해도 되는가?

**시점**: D-1 사전회의

**시스템**: 작업관리대장 서버

**활동**:
- 도급인 + 수급인 합동 검토
- 작업내용, 순서, 위험, 안전조치 재확인
- 필요 시 보완 요청
- 최종 확정 또는 보류 결정

**책임자**: 도급인 관리자, 수급인 관리자

**결과**:
- 확정 시 → D-Day 안전관리 앱으로 데이터 전달
- 보류 시 → 재검토 후 재확정

### 4.3 원칙 3: AI CHECK (AI 검증)

**질문**: 사람이 놓친 위험은 없는가?

**시점**: D-Day 작업 시작 전

**시스템**: 안전관리 앱 (AI 위험성평가 기능)

**활동**:
- D-1 확정 자료 + 안전정보 제공서를 AI에 입력
- JSA_DB 기반 유사 작업 검색
- 누락 위험요인 후보 제시
- 안전대책 후보 제시
- 사람이 최종 검토 및 확정

**책임자**: 수급인 작업책임자 (검토), AI (제안)

**원칙**:
- **AI는 제안, 사람이 결정**
- AI가 자동으로 위험성평가를 완료하지 않음
- 사용자가 선택한 항목만 공식 평가에 반영

### 4.4 원칙 4: EXECUTE (실행)

**질문**: 오늘 실제로 계획대로 안전하게 작업하고 있는가?

**시점**: D-Day 작업 중

**시스템**: 안전관리 앱

**활동**:
- 작업허가서 승인 및 작업 시작
- TBM 실시
- 실시간 현장 안전점검
- AI 사진 분석 (Phase 4)
- 작업 중 이행상태 점검 (3시간 이내 최초 확인)

**책임자**: 수급인 작업책임자 (실행), 도급인 작업담당자 (감독)

### 4.5 원칙 5: CONTROL (통제)

**질문**: 위험하면 즉시 멈출 수 있는가?

**시점**: 언제든지 (작업 중)

**시스템**: 안전관리 앱 (작업중지권)

**활동**:
- 누구나 작업중지 요청 가능 (안전퀴즈 결과와 무관)
- 즉시 작업 중지 및 대피
- 위험 원인 조치
- 위험성평가 재검토
- 관리자 승인 후 작업 재개

**책임자**: 모든 작업자 (요청 권한), 재개 승인자 (관리자)

**원칙**:
- 작업중지권은 산업안전보건법 제52조가 보장
- 안전퀴즈 미합격자도 작업중지 요청 가능
- 작업중지 이력은 삭제 불가 (감사 대응)

### 4.6 원칙 6: CLOSE (종결)

**질문**: 작업이 안전하게 끝났는가?

**시점**: 작업 완료 시

**시스템**: 안전관리 앱 (전자종결)

**활동**:
- 작업자 전원 철수 확인
- 공구·자재 정리 확인
- 방호장치 복구 확인
- ILS/LOTO 해제 완료 확인
- 설비 인계
- 전자종결 처리
- 작업관리대장 결과 반영 (Phase B에서 자동)

**책임자**: 수급인 작업책임자 (신청), 도급인 관리자 (승인)

## 5. 전체 업무 흐름 (30단계)

### 5.1 D-1 이전 (계획)

작업관리대장 서버에서 수행한다.

**Phase A**: 관리자가 엑셀로 관리 후 안전관리 앱 대시보드에 업로드  
**Phase B**: 사내 서버에서 자동 Firestore 동기화

| # | 단계 | 담당 |
|---|---|---|
| 1 | 작업 등록 | 도급인 작업담당자 |
| 2 | 작업 유형 및 수행 주체 결정 | 도급인 작업담당자 |
| 3 | 작업표준 / 위험성평가 / 작업계획서 등록 | 도급인 + 수급인 |
| 4 | 안전정보 사전 준비 | 도급인 작업담당자 |
| 5 | D-1 도급인 + 수급인 사전회의 | 양측 관리자 |
| 6 | 사전 리뷰 및 보완 | 양측 관리자 |
| 7 | D-1 최종 확정 | 도급인 관리자 |

### 5.2 D-Day (실행)

안전관리 앱에서 수행한다.

| # | 단계 | 담당 |
|---|---|---|
| 8 | 수급인 / 작업자 앱 접속 | 수급인 작업자 |
| 9 | 안전정보 제공서 확인 (도급인 작성분) | 수급인 작업책임자 |
| 10 | 출입자 안전퀴즈 응시 | 수급인 작업자 |
| 11 | 작업 관련 확정자료 확인 | 수급인 작업책임자 |
| 12 | AI 위험성평가 (JSA_DB 기반) | 수급인 작업책임자 |
| 13 | 작업 전 안전 확인 (최종 게이트) | 수급인 작업책임자 |
| 14 | 안전작업허가서 신청 | 수급인 작업책임자 |
| 15 | 작업허가 검토 및 승인 | 도급인 허가자 |
| 16 | TBM 실시 (참석자 확인 + 서명) | 수급인 작업책임자 |
| 17 | 작업 시작 (모든 게이트 통과 후) | 수급인 작업자 |
| 18 | 현장 안전점검 (3시간 이내 최초) | 수급인 관리감독자 |
| 19 | AI 현장 위험 점검 (사진 분석, Phase 4) | 수급인 작업자 |
| 20 | 위험 발견 여부 판단 | 모든 작업자 |
| 21 | 정상 시 → 작업 계속 | 수급인 작업자 |
| 22 | 위험 시 → 작업중지권 발동 | 발견자 |
| 23 | 안전조치 실시 | 수급인 작업책임자 |
| 24 | AI 위험 재검토 | 수급인 + 도급인 |
| 25 | 작업재개 승인 | 도급인 관리자 |
| 26 | 작업 종료 신청 | 수급인 작업책임자 |
| 27 | 현장 복구 확인 | 수급인 + 도급인 |
| 28 | ILS / LOTO 해체 확인 | 도급인 작업담당자 |
| 29 | 전자종결 | 도급인 관리자 |

## 6. 사용자 권한 체계 (5단계)

### 6.1 권한 개요

이 시스템은 **5단계 사용자 권한**을 사용한다.

모든 사용자는 **관리자가 앱에서 사전 등록**해야 한다. QR 임시 접속이나 익명 사용은 지원하지 않는다.

### 6.2 5단계 권한 상세

#### 6.2.1 admin (시스템 관리자)

**역할**: 시스템 전체 관리 및 최고 결정권자

**주요 권한**:
- 사용자 등록 / 삭제 / 권한 부여
- 모든 데이터 조회
- **전자종결 후에도 데이터 수정 가능** (특별 권한)
- 시스템 설정 변경
- 데이터 백업 / 복구
- 통계 및 리포트 관리

**대상**:
- 안전환경부서 최고 담당자
- 시스템 운영 담당자

**주의**:
- 관리자 권한은 강력하므로 **신중하게 선정**
- 관리자 수정 시 별도 이력 없음 (본 정책)
- 관리자 선정 및 변경은 사내 결재 필수

#### 6.2.2 employer_manager (도급인 관리자)

**역할**: 도급인 측 관리 감독

**주요 권한**:
- 작업 등록 (Phase A: 엑셀 업로드)
- D-1 사전회의 주관
- 작업담당자 지정
- 작업허가 최종 승인
- 고위험작업 사전 승인
- 현장 안전 감독
- 안전정보 승인
- 작업재개 승인
- 전자종결 승인

**대상**:
- 안전관리자
- 부서 관리감독자
- 공장장 / 실장급

#### 6.2.3 employer_officer (도급인 작업담당자)

**역할**: 특정 작업의 도급인 측 실무 담당

**주요 권한**:
- 담당 작업 조회
- **안전정보 제공서 작성 및 제공** (수급인 작업 시)
- D-1 사전회의 참여
- 작업허가 검토
- 현장 이행 점검
- 작업종료 확인
- ILS 해제 확인

**대상**:
- 정비팀 담당자
- 생산팀 담당자
- 각 부서의 작업 담당자

#### 6.2.4 contractor_manager (수급인 관리자 / 작업책임자)

**역할**: 수급인 측 관리 및 작업 책임

**주요 권한**:
- 회사 작업 자료 조회
- 위험성평가 작성
- 작업계획서 제출
- 작업허가 신청
- TBM 실시 및 서명
- 작업자 등록 및 관리
- 현장 안전 관리
- 작업종료 신청
- 작업중지 요청

**대상**:
- 협력사 안전관리자
- 협력사 팀장 / 반장
- 작업 책임자

#### 6.2.5 worker (작업자)

**역할**: 실제 작업 수행

**주요 권한**:
- 안전정보 확인 (수령)
- 안전퀴즈 응시
- TBM 참석 및 서명
- 작업 전 안전 확인
- 개인 안전조치
- **작업중지권 행사** (권리)
- 작업 사진 촬영 (필요 시)

**대상**:
- 실제 작업을 수행하는 모든 인원
- 상시 협력사 소속 작업자
- 일회성 파견 작업자 (사전 등록 필수)

## 8. 각 앱의 역할 및 연결

### 8.1 앱 구성 개요

이 시스템은 **6개의 화면 그룹**으로 구성된다.

[안전관리 대시보드] ├─ 오늘 내 작업 ├─ 현재 단계 ├─ 빠른 실행 └─ 통계

## 9. 데이터 흐름

### 9.1 Firestore 컬렉션 구조

**Phase A (현재 ~ 서버 완성 전)**:

Firestore ├─ 작업DB (703건, 이미 이관됨) │ └─ {workId} : 작업 원본 │ ├─ jsaDatabase (86건, 이미 이관됨) │ └─ {jsaId} : JSA 안전 지식 DB │ └─ users (신규 - Phase 1에서 구축 예정) └─ {userId} : 사용자 정보


**Phase B (모든 컬렉션 이관 완료 후)**:

Firestore ├─ 작업DB │ └─ {workId} │ ├─ users │ └─ {userId} │ ├─ 협력사관리 │ └─ {contractorId} │ ├─ 작업자관리 │ └─ {workerId} │ ├─ jsaDatabase │ └─ {jsaId} │ ├─ 안전정보제공 │ └─ {safeinfoNo} │ ├─ 안전퀴즈 │ └─ {quizId} │ ├─ 위험성평가 │ └─ {riskId} │ ├─ 고위험작업승인 │ └─ {approvalNo} │ ├─ 작업허가 │ └─ {permitNo} │ ├─ TBM │ └─ {tbmNo} │ ├─ 긴급조치 │ └─ {emergencyNo} │ ├─ 작업중점검 │ └─ {inspectionNo} │ ├─ 가스측정기록 │ └─ {measurementId} │ └─ 이메일로그 └─ {logId}


### 9.2 자연키 규약

모든 컬렉션은 **자연키**를 문서 ID로 사용한다.

| 컬렉션 | 자연키 | 형식 | 예시 |
|---|---|---|---|
| 작업DB | workId | `{date}_{originalNo}` | `2026-08-27_5` |
| 안전정보제공 | safeinfoNo | `SIP-YYYYMMDD-SEQ3` | `SIP-20260827-001` |
| 안전퀴즈 | quizId | `QZ-YYYYMMDD-SEQ3` | `QZ-20260827-001` |
| 위험성평가 | riskId | `RA-YYYYMMDD-SEQ3` | `RA-20260827-001` |
| 작업허가 | permitNo | `PTW-YYYYMMDD-SEQ3` | `PTW-20260827-001` |
| TBM | tbmNo | `TBM-YYYYMMDD-SEQ3` | `TBM-20260827-001` |
| 긴급조치 | emergencyNo | `EM-YYYYMMDD-SEQ3` | `EM-20260827-001` |
| 작업중점검 | inspectionNo | `IN-YYYYMMDD-SEQ3` | `IN-20260827-001` |
| 고위험 승인 | approvalNo | `HRA-YYYYMMDD-SEQ3` | `HRA-20260827-001` |
| JSA_DB | jsaId | `JSA-{class}-6자리` | `JSA-WRK-000001` |

### 9.3 문서 간 참조 관계

**중심 키**:
- 작업 원본: `workId`
- 실행 허브: `permitNo`

**참조 관계도**:

[작업DB] {workId} ↑ │ 참조 │ [안전정보제공] {safeinfoNo} │ │ workId, safeinfoNo 참조 ↓ [위험성평가] {riskId} │ │ workId, safeinfoNo, riskId 참조 ↓ [작업허가] {permitNo} ← 실행 허브 │ ├─ TBM {tbmNo} : permitNo 참조 │ ├─ 긴급조치 {emergencyNo} : permitNo 참조 │ ├─ 작업중점검 {inspectionNo} : permitNo 참조 │ └─ 가스측정 {measurementId} : permitNo 참조


**중요 원칙**:
- 각 문서는 **상위 문서의 자연키만** 참조
- 데이터 복제 최소화
- 필요 시 요약 스냅샷만 저장 (감사 목적)

### 9.4 데이터 저장 vs 조회 원칙

**저장 (Write)**:
- 각 앱은 **자신의 컬렉션에만** 쓰기
- 예: 위험성평가 앱은 `위험성평가` 컬렉션에만 저장

**조회 (Read)**:
- 다른 앱의 데이터는 **자연키로 조회**
- 예: TBM 앱은 permitNo로 `작업허가` 조회

**연결 (Update)**:
- 상위 문서에 하위 문서 자연키 추가는 예외적으로 허용
- 예: 작업허가 문서에 tbmNo, riskId 추가

### 9.5 자동 채움 정책

**원칙**:
- URL에 **자연키만** 전달
- 받는 앱이 원본 데이터를 조회
- 자동 채움 필드는 **시각적으로 구분** (초록 배경)
- 사용자 수정 시 자동 표시 해제

**예시** (안전작업허가서 → TBM):

[안전작업허가서 완료] ↓ TBM 이동 링크 생성: TBM_v2.html?permitNo=PTW-20260827-001 ↓ [TBM 앱] URL에서 permitNo 파싱 ↓ Firestore에서 작업허가 문서 조회 ↓ 다음 필드 자동 채움:

협력사
작업 인원
작업 책임자
밀폐공간 여부
ILS 상태
관련 riskId ↓ 위험성평가 자동 채움 (riskId 있으면):
위험요인

안전대책
조치 담당자

### 9.6 Phase B 자동 동기화 (서버 완성 후)

**서버 → Firestore 동기화**:

[작업관리대장 서버] ↓ 작업 등록 이벤트 [Firestore Functions] (또는 Webhook) ↓ Firestore 작업DB 자동 저장 ↓ 안전관리 앱에서 자동 조회


**필요한 준비**:
- 서버 API 인증 (API Key)
- 필드 매핑 정의
- 오류 처리 및 재시도
- 관리자 알림

**참고**: Cloud Functions 미사용 정책이므로 Firebase Extensions 또는 직접 서버-Firestore 동기화 필요.

## 11. 화면 UX 원칙

### 11.1 UX 기본 원칙

이 시스템은 **현장 작업자가 사용하는 모바일 앱**임을 최우선으로 한다.

**5대 원칙**:

1. **한 화면 = 한 목적**: 복잡한 메뉴 대신 다음 단계로 유도
2. **손가락 우선**: 장갑 착용 상태에서도 조작 가능한 버튼 크기
3. **큰 글씨**: 밝은 현장에서도 읽기 편한 폰트
4. **오류 방지**: 필수 입력 미완료 시 다음 단계 진행 차단
5. **상태 명확**: 색상 + 아이콘 + 텍스트 병기

### 11.2 홈 화면 재설계

**기존 방식 (지양)**:
[빠른 실행 메뉴] 🎯 안전퀴즈 📋 안전정보 🔐 작업허가 📝 TBM 🤖 위험성평가 🛑 작업중지


문제점:
- 사용자가 "지금 뭘 해야 하는지" 알 수 없음
- 순서 없음
- 각 메뉴가 독립적으로 보임

**새로운 방식 (권장)**:
┌─────────────────────────┐ │ 📋 오늘 내 작업 │ │ │ │ 3라인 배관 교체 │ │ ○○건설 │ │ 위험도: 고위험 │ │ │ ├─────────────────────────┤ │ 📍 현재 단계 │ │ │ │ ✅ 안전정보 확인 │ │ ✅ 안전퀴즈 │ │ ✅ AI 위험성평가 │ │ ✅ 작업허가 │ │ ▶ TBM (현재 단계) │ │ ○ 작업 시작 │ │ ○ 작업 종료 │ │ │ │ [다음 단계 →] │ └─────────────────────────┘


**설계 원칙**:
- 사용자가 진행할 **단 하나의 버튼** 표시
- 완료 단계는 초록 체크 (✅)
- 현재 단계는 강조 (▶)
- 미완료 단계는 회색 (○)
- 한 번의 클릭으로 다음 화면 이동

## 12. 관리자 권한 정책

### 12.1 관리자 권한 개요

**본 프로젝트 정책**:
- **관리자는 모든 권한 보유**
- 별도 수정 이력 없음
- 신뢰 기반 운영

**대상**: `admin` 권한 사용자

**책임**:
- 시스템 무결성 유지
- 데이터 정확성 관리
- 감사 대응
- 사용자 관리

### 12.2 관리자 특별 권한

**일반 사용자와의 차이**:

| 기능 | 일반 사용자 | 관리자 |
|---|:---:|:---:|
| 데이터 조회 | 권한별 제한 | 모든 데이터 |
| 데이터 수정 | 자신의 작성 문서만 | 모든 문서 |
| 상태 변경 | 정해진 흐름만 | 임의 변경 가능 |
| **종결 후 수정** | ❌ | ✅ |
| **게이트 우회** | ❌ | ✅ |
| 사용자 등록/삭제 | ❌ | ✅ |
| 시스템 설정 | ❌ | ✅ |
| 백업/복구 | ❌ | ✅ |

### 12.3 종결 후 수정 정책

**원칙**:
- 관리자는 전자종결 후에도 데이터 수정 가능
- 오탈자, 오기재, 사후 보완 자유
- **별도 수정 이력 없음** (본 정책)

**예시 시나리오**:

**시나리오 1**: 오탈자 발견
작업 종결 후 3일 뒤: "작업 완료됨" → "작업 완료" (오탈자 수정)

관리자 화면에서 직접 수정 가능 별도 승인 불필요


**시나리오 2**: 사후 보완
작업 종결 후 감사 시: 필드 누락 발견 → 추가 입력

관리자가 직접 보완


**시나리오 3**: 실수 정정
작업자 수 오기재: 5명 → 6명 (실제 참여 인원)

관리자가 직접 수정


### 12.4 관리자 수정 시 시스템 처리

**자동 갱신**:
- `updatedAt`: 수정 시각 자동 갱신
- `updatedBy`: 수정한 관리자 계정
- Firestore/localStorage 자동 저장

**감사 로그**:
- Firebase Auth 로그에 로그인/작업 기록
- Firestore 자체 감사 로그 (Firebase Console에서 확인)
- 별도 애플리케이션 수정 이력 없음

**중요**:
- 시스템은 **수정 사실만** 기록
- **수정 이유, 원본 값**은 저장 안 함
- 이것이 본 프로젝트의 확정 정책

### 12.5 관리자 선정 및 관리

**관리자 선정 기준**:
- 안전환경부서 소속
- 시스템 운영 담당자
- 사내 결재 완료
- 개인정보 보호 서약

**권장 사항**:
- 관리자는 **최소한**으로 유지
- 예: 정관리자 1명 + 보조관리자 1~2명
- 관리자 변경 시 인수인계 필수

**관리자 계정 보안**:
- 강력한 비밀번호 (12자 이상)
- 정기 변경 (분기별)
- 다단계 인증 검토 (향후)
- 공용 계정 금지 (개인별 발급)

### 12.6 게이트 우회 정책

**관리자 게이트 우회 가능**:

관리자는 다음 게이트를 우회하여 진행 가능:
- 안전정보 미확인 상태에서 작업허가 승인
- 안전퀴즈 미합격자의 TBM 등록
- ILS 미확인 상태에서 종결
- 미흡 조치 미완료 상태에서 종결

**우회 시 주의**:
- Firebase Auth 로그에 자동 기록됨
- 사후 감사 시 확인 대상
- 반복적 우회는 시스템 남용

**권장**:
- 우회는 진짜 예외 상황에만 사용
- 우회 사유는 관리자 개인 기록으로 보관 (앱 외부)

### 12.7 데이터 삭제 정책

**원칙**: **삭제 없음, 상태 변경만**

**예시**:
- 작업 취소 → 상태 = `취소` (데이터 유지)
- 잘못 등록 → 상태 = `폐기` (데이터 유지)
- 사용자 퇴사 → users 상태 = `비활성` (계정 유지)

**예외**: 
- 개인정보 파기 요청 시
- 법적 보존 기간 경과 시
- 관리자 판단하에 삭제 (권장하지 않음)

**삭제 대신 권장**:
- 상태 필드 활용 (`retired`, `archived`, `deleted`)
- 필요 시 필터로 숨김
- 감사 대응 시 조회 가능

### 12.8 백업 정책

**자동 백업**:
- Firestore: Firebase 자체 백업 (관리자 콘솔)
- localStorage: 사용자 브라우저 (백업 대상 아님)

**수동 백업**:
- 관리자가 주기적으로 Firestore Export
- Firebase Console → Firestore → Export
- Cloud Storage 또는 로컬 저장

**권장 주기**:
- 일일: 자동 백업 (Firestore 기본)
- 주간: 관리자 수동 백업
- 월간: 오프사이트 저장

**복구 절차**:
- 문제 발생 시 관리자 판단
- 백업본에서 Import
- 사용자 안내 필수

### 12.9 사용자 관리 정책

**등록 절차**:
1. 관리자가 앱 내 사용자 관리 화면 접속
2. 신규 사용자 정보 입력 (이름, 소속, 역할, 이메일 등)
3. Firebase Auth 계정 자동 생성
4. 초대 이메일 발송
5. 사용자 최초 로그인 및 비밀번호 설정

**권한 변경**:
- 관리자만 가능
- 즉시 반영
- Firestore users 컬렉션 업데이트

**계정 비활성화**:
- 퇴사, 계약 종료 시
- 데이터 유지, 로그인만 차단
- 감사 이력은 계속 보존

**계정 삭제** (권장하지 않음):
- 완전 삭제는 매우 신중히
- 관련 데이터 처리 방안 결정 후
- Firebase Auth + Firestore 모두 삭제

### 12.10 감사 대응

**감사 요청 시**:
- 관리자가 데이터 제공
- Firebase Console 로그 활용
- Firestore 문서 이력 (updatedAt, updatedBy)

**증빙 자료**:
- 작업별 통합 리포트 (permitNo 기준)
- 사용자 활동 로그 (Firebase Auth)
- 시스템 접근 이력

**주의**:
- 개인정보는 최소한만 제공
- 법적 근거 확인 후 제공
- 사내 개인정보 정책 준수

## 13. AI 활용 원칙

### 13.1 AI의 위치

**AI는 보조 도구**이다.

**AI가 하는 것**:
- 위험요인 후보 제시
- 안전대책 후보 제시
- 유사 작업 검색
- 누락 사항 안내
- 통제 적정성 추천

**AI가 하지 않는 것**:
- 최종 위험도 결정
- 작업허가 자동 승인
- 법령 준수 여부 확정
- 사고 발생 예측
- 안전 책임 대체

**핵심 원칙**: **"AI는 제안, 사람이 결정"**

### 13.2 현재 AI 구현 상태

**Phase 1 완성** (2026-08 기준):

- JSA_DB Firestore 저장 (86건)
- 유사도 검색 (Jaccard 기반)
- 안전대책 카드 선택
- 매트릭스 + 통제 적정성 하이브리드

**Phase 2 계획** (향후):
- AI 자동 위험요인 보완
- 사진 기반 현장 점검
- 자연어 기반 위험 분석

**Phase 3 계획** (장기):
- 실시간 위험 예측
- 사고 패턴 학습
- 맞춤형 안전 교육

### 13.3 JSA_DB 활용

**컬렉션**: Firestore `jsaDatabase` (86건)

**활용 방식**:
[작업명 입력] ↓ [JSA_DB 검색] (Jaccard 유사도) ↓ [상위 5건 후보 표시] ↓ [사용자가 카드 선택] ↓ [대책 자동 채움] ↓ [사용자가 최종 확정]


**유사도 계산**:
- 작업명: 50%
- 작업 유형: 30%
- 작업 설명: 20%
- 임계값: 15% 이상

### 13.4 안전대책 태그 시스템

**출처별 태그**:

| 태그 | 의미 | 우선순위 |
|---|---|---|
| `[LAW]` | 법령 근거 | 최우선 |
| `[INT]` | 사내 기준 | 우선 |
| `[SOP]` | 작업 표준 | 우선 |

**AI 태그 구분**:
- AI가 제안한 대책은 반드시 `[AI]` 태그
- 사용자가 선택한 경우에만 공식 반영
- 자동 승인 없음

### 13.5 AI 사용 원칙

**원칙 1**: 사람의 판단 우선
- AI 제안은 참고용
- 최종 결정은 사용자
- AI 반대 판단도 존중

**원칙 2**: 투명성
- AI 사용 여부 명시
- 어떤 데이터를 참조했는지 표시
- 유사도 점수 공개

**원칙 3**: 학습 없음 (현재)

## 15. 확정 사항 및 미확정 항목

### 15.1 확정 사항

이 문서에서 최종 확정된 핵심 정책은 다음과 같다.

#### 15.1.1 시스템 아키텍처

**확정**:
- Phase A (수동) → Phase B (서버 자동) 이중 아키텍처
- 작업관리대장 서버 개발 완료 시 자동 전환
- 703건 작업DB 이미 Firestore 이관 완료
- 86건 JSA_DB 이미 Firestore 이관 완료
- Firestore 스키마는 Phase A/B 동일

**변경 불가**:
- 컬렉션명 (한글 유지: `작업DB`, `작업허가`, `TBM` 등)
- 자연키 형식 (workId, permitNo 등)

**변경 가능** (담당자 협의 후):
- Firestore Rules 세부 사항
- 인덱스 추가

#### 15.1.2 사용자 권한

**확정**:
- **5단계 권한**: admin / employer_manager / employer_officer / contractor_manager / worker
- **모든 사용자 사전 등록 필수** (일회성 업체 포함)
- QR 임시 접속 없음
- 익명 접속 없음

**등록 담당**: admin 또는 employer_manager

**변경 불가**:
- 5단계 권한 구조
- 사전 등록 원칙

#### 15.1.3 관리자 권한

**확정**:
- 관리자는 **모든 권한 보유** (전권)
- 종결 후 데이터 수정 가능
- 게이트 우회 가능
- **별도 수정 이력 저장 없음** (본 정책)

**시스템 자동 처리**:
- `updatedAt`, `updatedBy`는 자동 갱신
- Firebase Auth 로그는 자동 기록

**변경 불가**:
- 관리자 전권 원칙
- 별도 수정 이력 없음 정책

**향후 변경 검토 가능**:
- 필요 시 정정 이력 기능 추가 (별도 결정)

#### 15.1.4 업무 흐름

**확정**:
- 30단계 프로세스
- 도급인 직접작업 / 수급인 도급작업 분기
- 6대 원칙 (PLAN → CLOSE)
- 필수 게이트 (안전정보, 안전퀴즈, 위험성평가 등)

**변경 불가**:
- 안전정보 제공서 = 도급인 작성, 수급인 확인
- 작업중지권 = 모든 사용자 행사 가능
- 게이트 통과 없이 다음 단계 진행 불가 (관리자 우회 예외)

## 부록 A: 용어 정의

프로젝트에서 사용하는 주요 용어를 정의한다.

### A.1 시스템 용어

- **작업관리대장 서버**: 사내에서 개발 중인 작업 관리 시스템 (Phase B에서 연동)
- **안전관리 앱**: 이 프로젝트 (Firestore + HTML 앱)
- **Phase A**: 관리자가 엑셀로 수동 관리하는 현재 단계
- **Phase B**: 서버가 자동으로 Firestore에 동기화하는 향후 단계

### A.2 사용자 역할 용어

- **admin**: 시스템 관리자 (최고 권한, 전권)
- **employer_manager**: 도급인 관리자 (안전관리자, 부서장)
- **employer_officer**: 도급인 작업담당자 (실무 담당)
- **contractor_manager**: 수급인 관리자 / 작업책임자
- **worker**: 작업자 (실제 작업 수행)

### A.3 업무 용어

- **도급인**: 작업을 발주하는 회사 (POSCO FM)
- **수급인**: 작업을 수행하는 협력사
- **직접작업**: 도급인 소속이 직접 수행하는 작업
- **도급작업**: 수급인이 위탁받아 수행하는 작업
- **D-1**: 작업 하루 전 (사전 회의)
- **D-Day**: 실제 작업일

### A.4 데이터 용어

- **workId**: 작업 원본 자연키 (예: `2026-08-27_5`)
- **permitNo**: 작업허가 자연키 (예: `PTW-20260827-001`)
- **riskId**: 위험성평가 자연키 (예: `RA-20260827-001`)
- **tbmNo**: TBM 자연키 (예: `TBM-20260827-001`)
- **emergencyNo**: 긴급조치(작업중지) 자연키 (예: `EM-20260827-001`)
- **jsaId**: JSA_DB 자연키 (예: `JSA-WRK-000001`)

### A.5 안전 용어

- **PTW (Permit To Work)**: 안전작업허가
- **TBM (Tool Box Meeting)**: 작업 전 안전 교육
- **JSA (Job Safety Analysis)**: 작업 안전 분석
- **ILS (Isolation Lock System)**: 격리 잠금 시스템
- **LOTO (Lock Out Tag Out)**: 잠금 및 표시
- **PPE (Personal Protective Equipment)**: 개인보호구
- **MSDS (Material Safety Data Sheet)**: 물질안전보건자료
- **PSM (Process Safety Management)**: 공정안전관리
- **GIB**: ILS 시스템 관련 키 보관 장치

### A.6 상태 용어

- **대기중**: 아직 시작 안 됨
- **허가진행중**: 허가 신청됨, 승인 대기
- **허가완료**: 최종 승인됨
- **작업중**: 실제 작업 진행 중
- **작업중지**: 긴급 중지된 상태
- **작업완료**: 정상 종결됨

### A.7 게이트 (Gate)

- **게이트**: 다음 단계로 진행하기 위한 필수 조건
- **게이트 통과**: 조건 만족
- **게이트 우회**: 관리자가 예외적으로 통과 (권장하지 않음)

## 부록 B: 자주 묻는 질문 (FAQ)

### B.1 시스템 관련

**Q1**: 작업관리대장 서버는 언제 완성되나요?

**A**: 현재 개발 최종 단계에 있으며, 완성 시 Firestore와 자동 연동됩니다. 그전까지는 관리자가 엑셀로 수동 관리하는 Phase A 방식을 유지합니다.

---

**Q2**: 703건 데이터는 어디에 있나요?

**A**: Firestore `작업DB` 컬렉션에 저장되어 있습니다. 모든 앱은 이 데이터를 조회하여 사용합니다.

---

**Q3**: 오프라인에서도 작동하나요?

**A**: 부분적으로 작동합니다. Firestore는 오프라인 캐시를 지원하여 최근 조회한 데이터는 오프라인에서도 확인 가능합니다. 단, 신규 저장은 온라인 필요.

---

### B.2 사용자 관련

**Q4**: 협력사 직원도 앱을 사용하나요?

**A**: 네. 관리자가 사전 등록한 협력사 직원은 앱을 사용할 수 있습니다. 상시 협력사 / 일회성 업체 구분 없이 모두 사전 등록 필수입니다.

---

**Q5**: 안전퀴즈를 통과해야 하나요?

**A**: 작업 참여자는 유효한 합격 기록이 필요합니다. 단, **작업중지 요청은 안전퀴즈 결과와 무관**하게 누구나 할 수 있습니다.

---

**Q6**: 비밀번호를 잊었어요.

**A**: Firebase Auth 자체 재설정 기능을 사용합니다. 로그인 화면의 "비밀번호 재설정" 링크를 클릭하세요. 등록된 이메일로 재설정 링크가 발송됩니다.

---

### B.3 권한 관련

**Q7**: 관리자가 정말 모든 데이터를 수정할 수 있나요?

**A**: 네. 관리자는 종결 후에도 자유롭게 수정할 수 있습니다. 단, 관리자 선정은 신중히 이루어지며, Firebase Auth 로그에 활동 이력이 자동 기록됩니다.

---

**Q8**: 왜 별도 수정 이력을 남기지 않나요?

**A**: 시스템 단순화와 관리자 신뢰 기반 운영을 위한 정책입니다. 필요 시 향후 이력 기능 추가 가능합니다.

---

**Q9**: 도급인 작업담당자와 수급인 작업책임자의 차이는?

**A**:
- **도급인 작업담당자** (employer_officer): 도급인 측에서 특정 작업을 담당하는 실무자 (예: 정비팀 담당자)
- **수급인 작업책임자** (contractor_manager): 협력사에서 작업을 책임지는 사람 (예: 협력사 팀장)

역할 분리:
- 안전정보 제공서: **도급인 작업담당자가 작성**
- 위험성평가: **수급인 작업책임자가 작성**
- 작업허가: **수급인이 신청 → 도급인이 승인**

---

### B.4 안전 관련

**Q10**: 작업 중 위험을 발견하면 어떻게 하나요?

**A**: 즉시 **작업중지권**을 행사하세요. 앱에서 [작업중지 요청] 버튼을 누르고 상황을 입력하면 됩니다. 안전퀴즈 결과와 무관하게 누구나 사용 가능하며, 행사자에게 불이익은 없습니다.

---

**Q11**: 안전정보 제공서를 확인 안 하면 작업 못 하나요?

**A**: 네. 수급인 작업의 경우, **안전정보 제공서 확인이 필수 게이트**입니다. 미확인 시 다음 단계 진행이 차단됩니다. (관리자 우회 가능하나 권장 안 함)

---

**Q12**: 밀폐공간 작업 시 필수 확인 사항은?

**A**:
1. 최초 가스 측정 (산소, CO, CO₂, H₂S, LEL)
2. 3자 합동 확인 (원칙)
3. 1시간마다 재측정
4. 감시인 배치
5. 비상 통신 수단
6. 구조 장비

상세 기준은 `HIGH_RISK_WORK_POLICY.md` 참조.

---

### B.5 데이터 관련

**Q13**: 703건이 실제 회사 데이터인가요?

**A**: 네. 실제 작업관리대장 엑셀에서 이관된 데이터입니다. 관리자가 안전관리 대시보드의 엑셀 붙여넣기 기능을 통해 Firestore에 저장했습니다.

---

**Q14**: JSA_DB 86건은 어디서 왔나요?

**A**: 사내 축적된 위험성평가 자료를 표준화한 것입니다. Firestore `jsaDatabase` 컬렉션에 저장되어 있으며, 위험성평가 앱이 자동 검색하여 참조합니다.

---

**Q15**: 데이터가 삭제되면 어떻게 하나요?

**A**: 데이터는 원칙적으로 **삭제하지 않고 상태를 변경**합니다 (예: `폐기`, `취소`). 관리자 실수로 삭제될 경우 Firebase 자체 백업으로 복구합니다.

---

### B.6 AI 관련

**Q16**: AI가 위험성평가를 자동으로 하나요?

**A**: 아니요. **AI는 제안만 하고, 사람이 최종 결정**합니다. AI가 제안한 항목은 `[AI]` 태그로 구분되며, 사용자가 검토하여 선택한 것만 공식 평가에 반영됩니다.

---

**Q17**: 사진 분석 AI는 언제 도입되나요?

**A**: Phase 4 (선택 사항)에서 도입 예정입니다. Google Cloud Vision 또는 유사 서비스를 활용할 계획이며, 개인정보 보호를 위해 얼굴 인식은 하지 않습니다.

---
